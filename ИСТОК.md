## Executive Summary
Исток — кастомная мультиагентная система на Go (Clean Architecture), спроектированная для
универсальных задач: генерация кода, контент, аналитика, визуальные ассеты, DevOps. Система из
10 специализированных агентов, организованных в 4 уровня (Control Plane → Planning →
Execution → Verification), общается через типизированные JSON-сообщения по Event Bus.
Жизненный цикл каждой задачи управляется конечным автоматом (FSM) с retry logic, circuit breaker
и экспоненциальным backoff.
Ключевые решения
10 агентов в 4-уровневой иерархии — минимум связности, максимум специализации
Event Bus на Go channels (+ Redis Streams для persistence) — zero external dependencies в core
FSM с 11 состояниями — полный контроль над жизненным циклом задачи
Clean Architecture — бизнес-логика изолирована от инфраструктуры, LLM-провайдеры
подключаются через интерфейсы
Exponential backoff + circuit breaker — отказоустойчивость без каскадных сбоев

## 3.3. Retry Policy
type RetryPolicy struct {
MaxAttempts     int           `json:"max_attempts"`      // default: 3
BaseDelay       time.Duration `json:"base_delay"`        // default: 2s
MaxDelay        time.Duration `json:"max_delay"`         // default: 120s
BackoffFactor   float64       `json:"backoff_factor"`    // default: 2.0
RetryableErrors []string      `json:"retryable_errors"`  // e.g. ["timeout", "rate_lim
## }
// Exponential backoff: delay = min(base * factor^attempt, max)
## // Attempt 1: 2s, Attempt 2: 4s, Attempt 3: 8s

## 3.4. Circuit Breaker
type CircuitBreaker struct {
State            CBState       `json:"state"`              // CLOSED | OPEN | HALF_OP
FailureThreshold int           `json:"failure_threshold"`  // default: 5
ResetTimeout     time.Duration `json:"reset_timeout"`      // default: 60s
FailureCount     int           `json:"failure_count"`
LastFailure      time.Time     `json:"last_failure"`
## }
Когда агент падает 5 раз подряд — circuit breaker переходит в OPEN, все задачи для этого агента
перенаправляются на fallback или ставятся в BLOCKED.

type EventBus interface {
Publish(ctx context.Context, event AgentMessage) error

## }

// Топики по конвенции
// task.*        — жизненный цикл задач

// tests.*       — результаты тестов
// security.*    — результаты проверок безопасности
// system.*      — health checks, метрики

Fallback: Redis Streams — для persistence, replay, и multi-instance deployment.

ErrTransient  ErrorClass = "transient"   // Retry: таймаут, rate limit, 5xx
ErrPermanent  ErrorClass = "permanent"   // Не retry: невалидный input, 4xx
ErrResource   ErrorClass = "resource"    // Retry с backoff: OOM, диск, квота LLM
ErrLogic      ErrorClass = "logic"       // Не retry: баг в агенте, assertion failed
## )
7.2. Стратегия обработки
Класс ошибкиRetry?Действие
transientДа, exponential backoffПовторить через 2s → 4s → 8s
permanentНетПеревести задачу в FAILED, уведомить
resourceДа, с увеличенным таймаутомПереключить на менее ресурсоёмкую модель
logicНетЛогировать stack trace, FAILED
7.3. Каскадная отказоустойчивость
## Agent Failure
## │
## ├─→ Retry Policy (max 3)
## │       │
│       ├─→ Success → продолжить
│       └─→ Fail → Circuit Breaker check
## │                    │
│                    ├─→ CLOSED → retry
│                    ├─→ OPEN → fallback agent или BLOCKED
│                    └─→ HALF_OPEN → probe с лёгкой задачей
## │
└─→ Dead Letter Queue (DLQ) → ручной разбор
